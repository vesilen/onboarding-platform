# Azure infrastructure (Terraform)

Terraform code for the `dev` environment of the onboarding platform in the i8c subscription
(CodeBaseX tenant), region Belgium Central.

## Two stacks

The code is split into two independent root modules, each with its own state:

| Stack | Lifecycle | Contents |
|---|---|---|
| `foundation/` | **Kept** (until `expiry`) | Managed identities, Key Vault, secret, Key Vault role assignments |
| `app/` | **Destroyed nightly** | App Service plan, web app, Function App + storage, Service Bus namespace + queue, Service Bus role assignments |

Why this split:

- The **user-assigned identity** keeps the same `principal_id`, so the Key Vault role assignment
  stays valid; a recreated web app just attaches the existing identity.
- The **Key Vault** cannot be recreated with the same name for 7 days after deletion (soft-delete),
  and the secret value stays stable.
- The App Service plan (B1) and the Service Bus namespace (Standard) are what cost money, so they go away
  at night. Messages still in the queue are lost; acceptable for dev.

`app/` does not read the foundation state: it looks up the identity and the vault **by name** with
`data` sources. Apply `foundation/` first.

## What Terraform manages

| Stack | Resource | Name | Purpose |
|---|---|---|---|
| – | Resource group | `rg-ivaninterview-dev` | **Not managed** – existing, read via a `data` source |
| foundation | User-assigned identity | `id-ivaninterview-api-dev-bec` | Identity of the API, survives the nightly destroy |
| foundation | Key Vault | `kv-ivaninterview-dev-bec` | Holds the application secrets (RBAC mode, 7-day soft-delete) |
| foundation | Secret | `kyc-api-key` | Generated by `random_password`, read by the API at startup |
| foundation | Role assignment | Key Vault Secrets Officer | Whoever runs Terraform may write secrets |
| foundation | Role assignment | Key Vault Secrets User | The API's managed identity may read secrets |
| foundation | User-assigned identity | `id-ivaninterview-func-dev-bec` | Identity of the Function, survives the nightly destroy |
| app | App Service plan | `asp-ivaninterview-dev-bec` | Linux, B1 |
| app | Web app | `app-ivaninterview-dev-bec` | Runs `onboarding-api` as a Java 21 JAR with the user-assigned identity |
| app | Service Bus namespace | `sb-ivaninterview-dev-bec` | Standard tier, SAS keys disabled (Entra ID only) |
| app | Queue | `application-submitted` | ApplicationSubmitted events; 5 deliveries then dead-letter; duplicate detection 10 min |
| app | Role assignment | Azure Service Bus Data Sender (queue) | The API may send |
| app | Role assignment | Azure Service Bus Data Receiver (queue) | The Function may receive |
| app | Role assignment | Azure Service Bus Data Owner (namespace) | Whoever runs Terraform: test from laptop / Service Bus Explorer |
| app | Storage account | `stivaninterviewdevbec` | Functions runtime storage (no hyphens allowed), accessed with the Function identity |
| app | Role assignment | Storage Blob Data Owner | The Function identity on its storage account |
| app | Function App | `func-ivaninterview-dev-bec` | Runs `onboarding-processor` (Java 21) on the same B1 plan, Always On |

The identity and the vault have `prevent_destroy = true`: a `terraform destroy` in `foundation/`
fails on purpose. Remove those lines for the final cleanup.

All resources carry the mandatory i8c tags `owner`, `purpose` and `expiry`.

## How the API reaches Key Vault

- Terraform sets the app settings `KEYVAULT_ENABLED=true` and `AZURE_KEYVAULT_ENDPOINT=<vault uri>`
  on the web app. App Service exposes them to the app as environment variables.
- Spring Cloud Azure authenticates with `DefaultAzureCredential`:
  - **in Azure**: the user-assigned managed identity (`AZURE_CLIENT_ID` tells it which one);
  - **locally**: your `az login` session (stored in `%USERPROFILE%\.azure`, shared by all terminals).
- Without `KEYVAULT_ENABLED=true` (CI, unit tests) Key Vault is not contacted at all.

## Usage

Prerequisites: Terraform >= 1.9, Azure CLI logged in to the CodeBaseX tenant.

```bash
export ARM_SUBSCRIPTION_ID=$(az account show --query id -o tsv)
export MSYS_NO_PATHCONV=1                            # Git Bash only: keep /subscriptions/... paths intact

# once per stack: fill in resource group, owner, expiry
cp infra/terraform/foundation/terraform.tfvars.example infra/terraform/foundation/terraform.tfvars
cp infra/terraform/app/terraform.tfvars.example infra/terraform/app/terraform.tfvars

terraform -chdir=infra/terraform/foundation init
terraform -chdir=infra/terraform/foundation apply   # once

terraform -chdir=infra/terraform/app init
terraform -chdir=infra/terraform/app apply          # every morning
```

Deploy the application (Terraform only creates an empty App Service, so redeploy after every
recreate):

```bash
./mvnw -B package -DskipTests
az webapp deploy \
  --name $(terraform -chdir=infra/terraform/app output -raw api_name) \
  --src-path services/onboarding-api/target/onboarding-api-0.1.0-SNAPSHOT.jar \
  --type jar
curl $(terraform -chdir=infra/terraform/app output -raw api_url)/actuator/health
```

End of the day:

```bash
terraform -chdir=infra/terraform/app destroy
```

Run locally against the real vault:

```bash
KEYVAULT_ENABLED=true \
AZURE_KEYVAULT_ENDPOINT=$(terraform -chdir=infra/terraform/foundation output -raw key_vault_uri) \
./mvnw -pl services/onboarding-api spring-boot:run
```

## State

- The state is **local**, one `terraform.tfstate` per stack (ignored by Git). The foundation state contains the
  generated secret value – never commit it.
- It lives outside Azure on purpose, so it survives cleaning up the resource group.

## Lifecycle and drift

Terraform is not a running service: it only changes Azure when you run `plan`/`apply`/`destroy`.

**If a resource is deleted outside Terraform** (portal, `az`):

- it stays gone until the next `terraform apply`;
- `terraform plan` detects the difference with the state (*drift*) and plans to recreate it;
- a recreated web app reuses the **same user-assigned identity**, so the Key Vault role
  assignment is untouched (with a system-assigned identity it would be replaced every time);
- the deployed JAR is **not** restored – run `az webapp deploy` again.

**Preferred cleanup is `terraform destroy`**, not deleting in the portal: the state then stays in
sync with reality and the next `apply` is predictable.

## Key Vault soft-delete

- A deleted vault stays *soft-deleted* and its name stays reserved (globally) for the retention
  period: 7 days for this vault, 90 days for vaults created with `az` defaults.
- Purging requires rights at **subscription** scope, which we don't have
  (`Microsoft.KeyVault/locations/deletedVaults/*`). Therefore
  `purge_soft_delete_on_destroy = false`.
- Consequence: destroying and recreating the vault with the same name fails until the retention
  period has passed. Keep the vault, or give it a random name suffix if it must be recreated.

## Known pitfalls

| Symptom | Cause | Fix |
|---|---|---|
| `MissingSubscription` on `az role assignment create` | Git Bash rewrites `/subscriptions/...` into a Windows path | `export MSYS_NO_PATHCONV=1` |
| 403 on the secret during the first `apply` | New role assignment not active yet | Run `terraform apply` again |
| 403 from Key Vault at app startup in Azure | Managed identity role not active yet | Wait a minute, `az webapp restart` |
| 403 `resourceGroups/read` on `plan` | Wrong resource group name (you only have rights on your own RG) | Check `terraform.tfvars` |
| `AuthorizationFailed ... deletedVaults/read` | Purge needs subscription-level rights | Ask the subscription owner, or avoid purging |
| 401/403 from Service Bus or Function storage right after the morning `apply` | Recreated role assignments not active yet | Wait a few minutes, `az webapp restart` / `az functionapp restart` |
| Namespace name already in use on `apply` | Name not released yet right after a destroy | Wait a few minutes, `apply` again |
| Function does not pick up messages | Always On off, or the JAR was not redeployed after the recreate | Check `always_on`, redeploy the Function |
